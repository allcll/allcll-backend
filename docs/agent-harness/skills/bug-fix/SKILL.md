# 올클 버그 수정 가이드

## 기본 원칙

bug-fix는 **의도적인 동작 변경**을 다룬다. 현재 동작이 기대 동작과 다르고, API 응답·검증·권한·저장 결과·알림·스케줄 상태처럼 외부 관찰 가능한 결과를 바꿔야 할 때 사용한다.

애매하면 먼저 `../shared/implementation-boundary.md`를 읽고 primary skill을 판정한다. 검증/권한/응답 변경, scheduler/SSE, 사용자 변경 보호가 중요한 작업이면 `references/gotchas.md`도 읽는다. 수정안 리뷰, PR 준비, 완료 판단처럼 작업 품질을 평가해야 하면 `references/quality-criteria.md`를 읽는다.

## 적용 대상

- 보고된 버그 수정
- validation, authorization, 응답 status/body처럼 동작을 바꾸는 검증 로직 추가
- 이미 기대 동작이 확정된 단일 엔드포인트 수준의 작은 보정
- analysis finding으로 결함이 확인된 뒤의 후속 수정

## 적용하지 않는 대상

- 원인이나 병목이 아직 불명확한 요청: `allcll-analysis`가 primary
- 동작 보존 cleanup, 중복 제거, 구조 개선: `allcll-refactoring`이 primary
- 테스트 작성/수정 자체가 목표: `allcll-testing`이 primary
- 큰 기능, 정책 엔진, 도메인 모델 재설계: 구현 전에 사용자 확인 또는 설계 단계

## 작업 순서

1. **경계 판단**
   - 현재 요청이 동작 변경인지 확인한다.
   - "분석 후 고쳐줘"는 먼저 analysis finding을 만든 뒤 결함이 확인될 때 bug-fix로 넘어온다.
   - 수정 중 동작 보존 정리 욕구가 생기면 같은 diff에 섞지 말고 refactoring 후보로 분리한다.

2. **현재/기대 동작 분리**
   - 현재 동작: 지금 코드가 어떤 입력/상황에서 어떻게 동작하는지 적는다.
   - 기대 동작: 사용자 또는 정책이 원하는 결과를 적는다.
   - 둘의 차이를 이번 수정의 완료 기준으로 삼는다.
   - 현재 동작을 재현할 수 없거나 원인이 추정이면 수정부터 하지 않고 확인 필요로 남긴다.

3. **기존 패턴과 영향 범위 확인**
   - 비슷한 controller, DTO, service, exception handler, test fixture를 `rg`로 찾는다.
   - validation/authorization 변경이면 `references/gotchas.md`의 컨테이너 트리거 짝을 확인한다.
   - 같은 패턴의 파일을 전수 확인하고 "N개 확인, 동일 결함 M개"처럼 결과를 남긴다.
   - 인접 문제를 발견해도 요청 범위 밖이면 수정하지 않고 분리 보고한다.

4. **최소 구현**
   - 기존 컨벤션과 패턴을 따른다.
   - 새 의존성, 새 추상화, 광범위한 rename을 피한다.
   - 사용자 기존 변경이 있는 파일은 덮어쓰지 않는다.
   - 민감 설정 파일 값은 읽거나 출력하지 않는다.

5. **검증**
   - 가능하면 재현 테스트를 먼저 추가한다.
   - 최소한 버그 케이스와 정상 케이스를 검증한다.
   - 컴파일만으로 완료 선언하지 않는다.
   - 테스트 실패를 삭제, 비활성화, 기대값 완화로 해결하지 않는다.
   - 관련 테스트를 실행하지 못했으면 이유와 대체 검증을 명시한다.

## 완료 조건

- primary가 bug-fix인 이유와 다른 skill이 primary가 아닌 이유를 판단했다.
- 현재 동작, 기대 동작, 재현/확인 조건이 분리되어 있다.
- 영향 범위를 실제 검색했고 결과를 보고했다.
- 구현 diff가 기대 동작 변경에 필요한 최소 범위다.
- 검증 명령 또는 미실행 사유가 있다.
- 분리한 인접 문제와 다음 단계가 "해당 없음"까지 포함해 보고됐다.
- PR/리뷰 단계에서는 `references/quality-criteria.md` 기준으로 문제 정의, 원인 근거, 영향 범위, 검증을 점검했다.

## 실패 시 행동

- 원인 미확정: analysis로 되돌려 finding과 확인 지표를 먼저 만든다.
- 동작 보존 작업으로 판정: refactoring으로 분기한다.
- 테스트만 필요한 상황: testing으로 분기한다.
- 범위가 커짐: 구현을 멈추고 분할안과 사용자 확인 항목을 보고한다.
- 민감 파일 확인이 필요함: 파일을 열지 말고 redacted evidence를 요청한다.
- 사용자 변경과 충돌: 임의 해결하지 말고 현재 상태와 선택지를 보고한다.

## 자가 보고 형식

작업 끝나면 아래 5개를 모두 적는다. 해당 사항이 없으면 "해당 없음"으로 적는다.

1. 변경 파일 목록과 라인 수
2. 변경 핵심 한 줄 요약
3. 검증 단계 결과
4. 분리한 인접 문제
5. 다음 단계 제안

## 절대 원칙

- 버그 재현 또는 확인 기준 없이 "고쳤다"고 하지 않는다.
- 사용자가 명시한 범위 밖 문제를 임의 수정하지 않는다.
- 응답 형식, API 계약, 예외/로그 메시지 변경은 동작 변경으로 취급한다.
- `allcll-crawler`, `.env`, `application-local.yml`, credentials, service account JSON, token/private key 값은 읽거나 출력하지 않는다.
- 기존 사용자 변경을 되돌리지 않는다.
