# 버그 수정 품질 기준

bug-fix 결과가 "그럴듯한 수정"이 아니라 실제로 리뷰 가능한 수정인지 판단할 때 사용한다.

## 필수 평가 축

| 축 | 통과 기준 | 실패 신호 |
|---|---|---|
| 문제 정의 | 현재 동작, 기대 동작, 재현/확인 조건이 분리되어 있다. | "문제인 것 같음"만 있고 어떤 입력에서 어떻게 틀리는지 없다. |
| 원인 근거 | 수정 위치와 호출 경로가 설명된다. | 한 파일만 보고 원인을 단정한다. |
| 영향 범위 | 같은 패턴/도메인/호출자를 실제 검색하고 결과를 남긴다. | "비슷한 곳도 있을 수 있음"으로 끝난다. |
| 수정 크기 | 기대 동작을 바꾸는 데 필요한 최소 diff다. | cleanup, rename, 새 추상화가 같이 섞인다. |
| 검증 | 버그 케이스와 정상 케이스를 테스트나 명령으로 확인한다. | 컴파일만 실행하거나 테스트 실패를 설명 없이 넘긴다. |
| 보고 | 변경 파일, 검증 결과, 분리한 인접 문제, 다음 단계를 적는다. | "수정했습니다"만 남긴다. |

## 좋은 bug-fix 산출물

- "현재는 A 입력에서 B가 발생하고, 기대는 C다"가 먼저 나온다.
- 재현 테스트를 만들 수 있으면 먼저 만들고, 어렵다면 재현 로그/수동 검증 조건을 적는다.
- validation/authorization 수정은 어노테이션 자체와 트리거 컨테이너를 함께 점검한다.
- 같은 패턴의 파일을 검색해 "이번 수정 범위"와 "별도 보고 범위"를 나눈다.
- 테스트를 삭제하거나 기대값을 느슨하게 하지 않는다.
- 원인이 추정이면 수정하지 않고 analysis 후속으로 되돌린다.

## 리뷰 질문

- 이 diff가 없으면 어떤 버그가 계속 재현되는가?
- 이 diff가 있으면 어떤 테스트/명령이 새 기대 동작을 증명하는가?
- 정상 케이스가 깨지지 않았다는 근거가 있는가?
- 같은 문제가 있을 수 있는 곳을 실제로 확인했는가?
- 인접 리팩토링이나 큰 설계 변경이 섞이지 않았는가?
- 민감 파일, 사용자 변경, 별도 repo 경계를 건드리지 않았는가?

## 완료 판정

아래 중 하나라도 없으면 완료가 아니라 "확인 필요" 또는 "검증 미완료"로 보고한다.

- 현재/기대 동작
- 재현 또는 확인 조건
- 영향 범위 검색 결과
- 최소 수정 근거
- 버그 케이스와 정상 케이스 검증 결과 또는 미실행 사유
