# 리팩토링 품질 기준

refactoring 결과가 "코드가 예뻐짐"이 아니라 동작 보존을 증명할 수 있는지 판단할 때 사용한다.

## 필수 평가 축

| 축 | 통과 기준 | 실패 신호 |
|---|---|---|
| 범위 | 수정할 파일/메서드와 금지할 변경을 먼저 정한다. | 하다 보니 여러 패키지로 번진다. |
| baseline | 수정 전 관련 테스트 또는 대체 검증을 확보한다. | 변경 전 상태를 모른 채 수정한다. |
| 보존 동작 | 반환값, 예외, 메시지, 저장 순서, scheduler timing 등 보존 대상을 적는다. | "동작 동일"이라고만 말한다. |
| diff 성격 | 구조 변경만 있고 외부 관찰 동작 변경이 없다. | 로그/응답/예외/타이밍/transaction이 같이 바뀐다. |
| 재검증 | baseline과 같은 검증을 변경 후 다시 실행한다. | 테스트를 고쳐서 통과시키거나 다른 테스트만 돌린다. |
| 분리 보고 | 발견한 버그나 정책 변경 후보를 bug-fix/analysis로 분리한다. | 오타, 메시지, 정책 값을 같이 고친다. |

## 좋은 refactoring 산출물

- "이번 변경에서 보존할 경로"가 구체적이다.
- 관련 테스트를 수정 전/후 같은 조건으로 실행한다.
- 테스트가 없으면 바로 구현하지 않고 수동 검증 시나리오나 testing 후속을 제안한다.
- 성능 개선은 결과 의미를 유지하는 범위에서만 진행한다.
- benchmark 없이 개선율, 동접 수용 가능 여부, p95 감소치를 단정하지 않는다.
- 실패한 테스트는 구현을 다시 보게 하는 신호로 다룬다.

## 리뷰 질문

- 변경 전 baseline을 실제로 확보했는가?
- 변경 후 같은 검증을 다시 실행했는가?
- public contract, 메시지, 로그, 정렬/필터, transaction, scheduler timing이 보존되는가?
- 테스트 기대값이나 fixture를 리팩토링에 맞춰 바꾸지 않았는가?
- 성능 개선이라면 무엇이 측정됐고 무엇은 추정으로 남겼는가?
- 범위 초과나 동작 변경 후보를 분리 보고했는가?

## 완료 판정

아래 중 하나라도 없으면 완료가 아니라 "baseline 부족", "검증 미완료", 또는 "bug-fix/analysis 분기 필요"로 보고한다.

- 수정 전 baseline 또는 baseline 부재 보고
- 보존해야 할 동작 목록
- 최소 구조 변경 근거
- 변경 후 같은 검증 결과
- 테스트 무수정 또는 승인된 별도 테스트 작업 근거
