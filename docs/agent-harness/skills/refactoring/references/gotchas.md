# 리팩토링 gotchas

refactoring 작업에서 반복해서 실패하기 쉬운 지점을 고정한다. 성능 개선, 중복 제거, scheduler/SSE, 외부 연동, 테스트 부재 작업이면 읽는다.

## baseline 먼저

- 수정 전에 관련 테스트를 실행한다.
- 관련 테스트가 없으면 바로 구현하지 말고 수동 검증 시나리오나 테스트 추가 필요성을 보고한다.
- 환경 의존 실패가 있어도 변경 전후 같은 실패면 회귀 없음의 근거가 될 수 있다.
- baseline 없이 "동작 보존"이라고 말하지 않는다.

## 보존해야 할 동작

리팩토링은 아래를 바꾸지 않는다.

- 반환값, 예외 타입과 메시지, 로그 메시지, API 응답
- 정렬/필터 순서, 저장 순서, transaction boundary
- scheduler 주기, retry 횟수, 외부 API 호출 횟수
- public signature, Bean wiring, profile/config behavior
- 테스트 기대값

문자열 오타처럼 명백해 보여도 외부 관찰 가능하면 bug-fix 후보로 분리 보고한다.

## 성능 개선 판정

- 병목 원인을 모르면 analysis로 먼저 분기한다.
- 같은 결과를 더 적은 반복/할당/쿼리로 만드는 변경이면 refactoring이다.
- scheduler 주기, 알림 timing, retry, timeout, 외부 호출 횟수를 바꾸면 동작 변경이다.
- benchmark 없이 개선율, 동접 수용 가능 여부, p95 감소치를 단정하지 않는다.

## 테스트 실패 처리

- 테스트를 고쳐서 리팩토링을 통과시키지 않는다.
- 실패가 구현 문제면 되돌리고 다시 작게 시도한다.
- 기존 실패라면 baseline과 같은 실패인지 근거를 남긴다.
- 테스트가 현재 동작을 잘못 고정하고 있다고 판단되면 testing 또는 bug-fix 후속으로 분리한다.

## 멈춤 조건

- 범위가 파일 3개, 50줄, 함수 2개를 넘을 가능성이 크다.
- 외부 mock 전략, 정책 판단, public API 계약 변경 여부가 불명확하다.
- 민감 파일을 읽어야만 판단할 수 있다.
- `allcll-crawler` 등 별도 repo 경계를 넘어야 한다.
